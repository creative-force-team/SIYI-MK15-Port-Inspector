## Проверки версии 1.3.1

Версия 1.3.1 исправляет критическую неопределённость предыдущего опыта: официальный SIYI SDK UART `/dev/ttyHS0` теперь перед открытием переводится в raw-режим с 115200 бод через доступный `stty/toybox stty`. Результат настройки попадает в диагностический snapshot.

Если после активного поиска не приходит ни одного валидного SIYI-кадра, приложение явно сообщает на экране, что нужно проверить `SIYI TX -> Datalink -> Connection`.

GitHub Actions run: `35789984061` — **success**. Прошли PowerShell syntax check, все host-tests, Android Gradle build и публикация APK.


## Проверки версии 1.3.2

Из реального аппаратного отчёта 1.3.1 извлечён повреждённый UART0-кадр:

```text
75 66 02 20 00 0C 00 68 ... 1D BB
```

Установлено, что это SIYI `0x48`, прошедший через TTY IUCLC:
- `55 -> 75`;
- `48 -> 68`.

После восстановления этих байтов CRC из самого аппаратного кадра точно совпадает: `0xBB1D`.

Этот реальный кадр добавлен в `ProtocolSelfTest`. Тест требует:
- восстановить заголовок и команду;
- пройти исходный аппаратный CRC;
- декодировать фактический mapping MK15;
- подтвердить `CH10=C`, `CH11=D`.

Кроме parser fallback, UART0 теперь явно получает `-iuclc` и приложение сохраняет эффективный `stty -a`.


## Проверки версии 1.3.3

Аппаратный отчёт 1.3.2 подтвердил mapping, но не дал ни одного `0x42` channel frame. В эффективном `stty -a` после открытия Java-stream снова был включён `iuclc`.

1.3.3 меняет порядок: ttyHS0 сначала открывается, затем получает 115200 raw и `-iuclc`; эффективные флаги проверяются уже после открытия.

Активный исследователь сначала отправляет **точную официальную команду 4 Гц** (`freq=2`). Если живых channel frames нет, только тогда пробует 20 Гц.


## Аппаратная улика 1.3.3 → исправление 1.3.4

В отчёте 1.3.3 effective `stty -a` показал положительный `istrip`.

Два реальных повреждённых mapping-кадра дают точное доказательство:

```text
calculated CRC = B5 2D
received CRC   = 35 2D

calculated CRC = 80 4A
received CRC   = 00 4A
```

В обоих случаях входной TTY ровно очистил старший бит. Это соответствует `ISTRIP`.

1.3.4 явно задаёт `-istrip -inpck -ignpar -parmrk` после открытия UART0 и отдельно помечает в журнале CRC-повреждения, полностью объясняемые ISTRIP.

Кроме того, 0x42 теперь тестируется изолированно: mapping до запуска потока, затем только три одинаковые команды 0x42 с sequence=0.


## Аппаратный отчёт 1.3.4 → версия 1.3.5

1.3.4 доказала, что `stty -F /dev/ttyHS0` возвращает rc=0, но последующее открытие/проверка снова видит vendor-default termios с IUCLC/ISTRIP. Следовательно, настройка через отдельное открытие пути не является надёжной на этом драйвере.

1.3.5 использует same-FD shell bridge: UART открывается один раз как fd3, `stty` применяется к fd3 через stdin redirection и этот же fd остаётся открыт для всего обмена.

Также устранена гонка сценария, из-за которой AUTO мог отправить 0x42 до PRE-RC mapping.

## Локальная сборка 1.4.0: устранение зависимости от ndk-build

На Windows NDK 28.2 был найден корректно, однако `ndk-build` отказался признавать реально существующий `Android.mk` по абсолютному пути проекта с пробелами/`!`.

Это не ошибка NDK 28.2 как компилятора. Проблемным оказался путь `APP_BUILD_SCRIPT` в связке Gradle -> ndk-build/GNU Make.

Исправление:
- Gradle больше не запускает `ndk-build`;
- `mk15serial.c` компилируется напрямую NDK Clang для `aarch64-linux-android23`;
- результат проверяется как AArch64 ELF;
- Gradle только упаковывает готовый `libmk15serial.so`.
